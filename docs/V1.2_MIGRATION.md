# Migrating to v1.2

v1.2 adds security controls without silently changing the behavior of an
existing configuration. The distributed `config.yaml` adopts the safer
settings, while omitted keys retain compatibility defaults where a behavior
change would be disruptive.

## Before upgrading

1. Back up the current configuration and audit artifacts.
2. Record which signing secret protects existing evidence. The verifier needs
   that same secret for legacy records.
3. Make every listen address explicit, especially for HTTP proxy deployments.
4. Test the new configuration against a non-production upstream and verify the
   resulting audit artifact before rollout.

## Signing now fails closed

Signing remains enabled by default, but an enabled signer now requires a
non-blank secret during configuration validation. No listener or stdio upstream
starts if the secret is absent.

Prefer an environment variable instead of storing the secret in YAML:

```bash
export MCP_AUDIT_SIGNING_SECRET="$(openssl rand -hex 32)"
```

`MCP_AUDIT_SIGNING_SECRET` has precedence over `audit.secret`. The legacy
`AUDIT_SECRET` environment variable remains supported at lower precedence.
Set `audit.sign: false` only when unsigned evidence is an explicit operational
decision.

New signed records keep the legacy `signature` and add Integrity v2. Existing
consumers can continue reading the legacy field while verification workflows
migrate to the complete critical-record signature. See
[AUDIT_INTEGRITY.md](AUDIT_INTEGRITY.md).

## Make HTTP exposure explicit

An omitted `proxy.bind_address` keeps the legacy all-interface bind in v1.2 and
emits a warning. The distributed configuration uses loopback. Set the intended
address explicitly:

```yaml
proxy:
  transport: http
  bind_address: 127.0.0.1
  port: 4422
```

Use a non-loopback address only with deliberate network controls, authentication,
and TLS. The dashboard continues to default to `127.0.0.1`; make that explicit
in managed configurations as well.

HTTP deployments should also review the new request bounds and allowlists:

```yaml
proxy:
  http:
    max_request_body_bytes: 10485760
    max_header_bytes: 1048576
    read_header_timeout: 10s
    read_timeout: 30s
    write_timeout: 30s
    idle_timeout: 120s
    allowed_origins:
      - https://mcp-client.example.com
    allowed_hosts:
      - mcp-gateway.example.com
```

Origin checks apply only when a browser sends an `Origin` header. Host entries
accept a hostname or IP address with an optional port. Invalid allowlist values
are rejected during startup.

## Choose the HTTP client identity mode

`auth.mode: none` preserves HTTP compatibility and uses the explicitly
configured static principal. It is appropriate only when a trusted network is
the authentication boundary. Stdio continues to derive its static principal
from `proxy.client_id` because process ownership is its trust boundary.

```yaml
auth:
  mode: none
  static:
    subject: local-operator
    client_id: desktop-client
    issuer: static
    roles: [operator]
    scopes: [mcp:read]
```

For a pre-shared HTTP credential, configure `static_bearer` and place the token
in the environment:

```bash
export MCP_AUDIT_STATIC_BEARER_TOKEN="$(openssl rand -hex 32)"
```

```yaml
auth:
  mode: static_bearer
  static:
    subject: automation
    client_id: ci-client
    issuer: static
    roles: [operator]
```

For an OIDC resource server, configure exact issuer and audience values plus a
JWKS endpoint:

```yaml
auth:
  mode: oidc
  oidc:
    issuer: https://login.example.com/tenant
    audience: mcp-audit
    jwks_uri: https://login.example.com/tenant/.well-known/jwks.json
    allowed_methods: [RS256]
    client_id_claim: client_id
    roles_claim: roles
    scopes_claim: scope
```

OIDC validates signature, issuer, audience, expiry, and not-before. Symmetric
JWT algorithms are not accepted. Remote issuer and JWKS URLs require HTTPS.

The inbound `Authorization` header is consumed as a gateway credential and is
stripped before forwarding by default. If the upstream MCP server independently
requires that same header, opt in only for a trusted upstream:

```yaml
proxy:
  forward_headers: [Authorization]
```

## Expand policy deliberately

When `policy.scope` is omitted, v1.2 keeps the legacy `tools_only` behavior.
The distributed config uses `all_operations`, which applies policy to every
client-originated MCP method.

```yaml
policy:
  enabled: true
  scope: all_operations
  default_action: allow
  rules:
    - id: RESOURCE-001
      action: deny
      issuer: https://login.example.com/tenant
      role: operator
      method: resources/read
      name: file:///restricted
      reason: Restricted resource
```

Rules remain ordered and first-match. Empty selectors and `*` are wildcards.
Legacy `client_id`, `server_id`, and `tool_name` selectors remain valid. New
selectors are `subject`, `issuer`, `role`, `scope`, `method`, and `name`. Add a
stable rule `id` to retain the matched rule in audit evidence. The generic
`mcp_name` audit field records non-tool object names while `tool_name` remains
unchanged for compatibility.

## Enable incoming TLS when needed

Incoming proxy TLS is separate from the existing upstream TLS settings:

```yaml
proxy:
  tls:
    enabled: true
    cert_file: /etc/mcp-audit/tls.crt
    key_file: /etc/mcp-audit/tls.key
```

The server requires both files and enforces TLS 1.2 or newer. Existing
`ca_file`, `server_name`, `client_cert_file`, and `client_key_file` settings
continue to configure the outbound connection to the upstream MCP server.

## Streamable HTTP metadata

MCP session, protocol-version, cache, and multi-round-trip headers are forwarded
unchanged. If `Mcp-Method`, `Mcp-Name`, or `Mcp-Protocol-Version` repeat values
found in the JSON-RPC body, the values must agree. A mismatch returns HTTP 400
with JSON-RPC code `-32600` before upstream forwarding.

Clients that previously sent contradictory advisory headers must correct or
remove them.

## Verify evidence after rollout

The verifier detects JSONL and SQLite automatically:

```bash
MCP_AUDIT_SIGNING_SECRET="current-secret" mcp-audit verify audit.jsonl
MCP_AUDIT_SIGNING_SECRET="current-secret" mcp-audit verify audit.db --json
```

Exit status `0` means all records are valid, `1` means at least one record is
invalid or unsigned, and `2` means a usage or input failure. Use `--key-id` when
the records use a non-default Integrity v2 key ID.

## Rollout checklist

- The signing secret is available to the service before startup.
- Proxy and dashboard bind addresses are explicit.
- Non-loopback HTTP endpoints have authentication, TLS, and network controls.
- OIDC issuer, audience, JWKS, algorithms, and claim names match issued tokens.
- `policy.scope` is chosen explicitly and principal-aware rules are exercised.
- Browser Origin and Host allowlists contain the deployed public values.
- A representative MCP operation reaches the intended upstream.
- Denied and successful operations produce terminal audit outcomes.
- `mcp-audit verify` returns status `0` for the resulting artifact.
