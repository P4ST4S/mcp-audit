# v1.3 audit durability and snapshot verification

v1.3 adds explicit verification policy and storage acknowledgement without
changing entry fields, legacy signatures, Integrity v2, RPC behavior, metrics,
or dashboard response shapes. Existing configs retain `audit.durable: false`;
default `verify` still accepts valid legacy-only evidence and empty artifacts.

## Opt into storage acknowledgement

```yaml
audit:
  durable: true
  async:
    enabled: true
```

With `durable: true`, a successful audit append has passed a backend durability
barrier: JSONL flushes and syncs the batch; SQLite commits with
`synchronous=FULL`. Async mode waits for that barrier instead of returning after
enqueue. This adds disk latency and backpressure; measure throughput on your
deployment filesystem. Without durable mode, JSONL flushes to the OS and async
mode can acknowledge entries still in memory.

Terminal finalization freezes the record ID, timestamp, payload and signatures
before its first append. Up to three attempts retry audit persistence only,
reconciling uncertain writes by record ID and complete stored content. Matching
records are acknowledged without appending again; conflicting identities or
unreadable evidence fail. A failed async worker remains observably failed, but
durable finalization can resolve its own record and retry directly after that
worker stops. Close retains the worker error even after successful recovery.

JSONL rolls back a failed batch and resets its buffered writer. Durable appends
refuse an existing tail without a newline, preserving damaged evidence for
operator inspection instead of concatenating new output onto it. Use one writer
per JSONL path; multiple processes writing or rotating one path are unsupported.
Pre-create the storage directory on a persistent local filesystem. On Unix the
file and its containing directory are synced; newly created ancestor directories
are outside that barrier. On Windows file contents are synced but directory
creation/rename persistence across power loss is not guaranteed. Filesystem,
device and host guarantees still apply; network filesystems may weaken them.

This is not a persistent replay queue: a crash before acknowledgement can leave
missing or partial evidence. Persistent write failures remain errors, and the
proxy still forwards MCP traffic independently of audit success. Successful MCP
traffic therefore does not itself prove a durable audit exists. Operational
metrics and traces remain visibility, not evidence or a recovery journal.
`tools/call` is never retried as part of audit recovery. Retention intentionally
deletes archives and bounds the evidence retained; export snapshots before it.

## SQLite concurrency and backups

SQLite now uses WAL, a 1-second busy timeout on each connection, and FULL
synchronous commits. Readers no longer block commits; another writer can still
cause a bounded lock error. Failed commits are rolled back or their connection
is discarded before reuse. Large batches have no artificial total-duration
deadline.

Use a local filesystem supporting WAL shared memory. Back up a running database
with SQLite's backup API/tooling, or stop writers and close the database before
copying. Copying only `audit.db` while `audit.db-wal` is live can omit committed
records; preserve the database and WAL together when required by your tooling.
Allow write access for the `-wal` and `-shm` sidecars. Rollback to v1.2 does not
remove WAL automatically; close all connections before changing journal mode.

## Require v2 and pin a snapshot

```bash
export MCP_AUDIT_SIGNING_SECRET='your-existing-signing-secret'
mcp-audit verify snapshot.jsonl --require-integrity-v2
mcp-audit checkpoint snapshot.jsonl --output snapshot.checkpoint.json
# Copy the checkpoint to a separately controlled trusted location.
mcp-audit verify snapshot.jsonl --checkpoint /trusted/snapshot.checkpoint.json
```

Use a closed/quiescent artifact. The same commands support SQLite. Checkpoint
creation requires valid, nonempty v2 evidence and a new output path; it refuses
to overwrite evidence or an existing checkpoint. Both commands accept the
existing `--key-id` and `--format` options, and `--json` for automation. Legacy
entries are not upgraded or re-signed automatically.

`verify` returns `1` for an entry/policy/checkpoint mismatch and `2` for usage or
input failures. Per-entry counters can all be valid while the checkpoint still
fails: check the exit status and `first_error`. Checkpoint creation returns `2`
if the source is ineligible or cannot be read, signed, or written.

Pin the expected checkpoint/version outside the artifact's write boundary.
Replacing both with an older valid pair defeats freshness; possession of the
HMAC secret permits forgery. A checkpoint verifies one retained snapshot, not
every historical operation, a live stream, or multiple rotated files. See
[the exact checkpoint format and trust limits](AUDIT_INTEGRITY.md).
